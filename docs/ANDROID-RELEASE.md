# Android Release Workflow

This document is the source of truth for producing Android artifacts for Singularity Deux. It exists to keep future Android updates reproducible and to prevent a desktop resource or a Git LFS pointer from being published as an Android media dependency.

## Artifact contract

Every release APK must satisfy all of these requirements:

- It contains the Android MPV native libraries loaded by `MpvPlugin.kt`: `libmpv.so` and `libplayer.so` for every ABI being published.
- It does not contain the Windows-only `libmpv-2.dll` resource.
- It does not contain Git LFS pointer text in place of a binary.
- It is signed, reports the version from the release tag, and passes `apksigner verify`.
- It launches and can initialize an MPV player on a supported Android device.

The APK size is not the correctness check. A working MPV build is expected to be larger than an APK that is missing its native media libraries.

## Source of native media libraries

The Kotlin bridge calls `System.loadLibrary("mpv")` and `System.loadLibrary("player")`. A clean checkout must therefore populate `src-tauri/gen/android/app/src/main/jniLibs/` before Gradle runs.

Do not rely on files left in `src-tauri/gen/android`; that directory is generated by `tauri android init`, and the native libraries are intentionally not build outputs that can be assumed to exist on a GitHub runner.

This repository now uses a checked-in, versioned bundle: `src-tauri/android-plugin/jniLibs/` contains the tested `arm64-v8a` and `x86_64` libraries as ordinary Git blobs (each file is below GitHub's per-file limit). `MPV_ANDROID_VERSION.txt` records the source build date (`2026-03-22`), and `SHA256SUMS.txt` is checked in with the bundle. If the bundle changes, update that marker and the checksums before publishing. Git LFS remains reserved for the Windows DLL.

Building the MPV Android native libraries from a pinned upstream commit in a dedicated, cached CI job remains a possible longer-term replacement, but it must produce the same JNI API and pass the same APK checks before it replaces the checked-in bundle.

The [official `mpv-android` repository](https://github.com/mpv-android/mpv-android) is an Android application and states that it is not an importable AAR. Do not solve the missing libraries by adding `is.xyz.mpv:mpv-android` as a normal Gradle dependency without first verifying the artifact and JNI API compatibility.

## Required GitHub Actions sequence

The Android job in `.github/workflows/build.yml` must perform these steps in order:

1. Check out the repository. Android native libraries are ordinary Git blobs; the Windows job separately enables Git LFS for the desktop DLL.
2. Install the pinned Node, Java, Android SDK, NDK, and Rust targets.
3. Stamp the Android version from the release tag before Android initialization.
4. Run `npm ci` and `npm run tauri android init`.
5. Copy the Kotlin plugin files and the pinned Android `jniLibs` bundle into the generated project.
6. Remove the desktop `libmpv-2.dll` resource from the Android configuration/assets. Windows keeps this resource; Android does not.
7. Apply signing configuration from GitHub Secrets. Never use local keystore paths or fallback passwords in CI.
8. Build each supported Android target with only its matching native-library directory in
   `src-tauri/gen/android/app/src/main/jniLibs/`:

   ```bash
   rm -rf src-tauri/gen/android/app/src/main/jniLibs
   mkdir -p src-tauri/gen/android/app/src/main/jniLibs
   cp -R src-tauri/android-plugin/jniLibs/arm64-v8a \
     src-tauri/gen/android/app/src/main/jniLibs/
   npm run tauri android build -- --apk --target aarch64 --ci

   rm -rf src-tauri/gen/android/app/src/main/jniLibs
   mkdir -p src-tauri/gen/android/app/src/main/jniLibs
   cp -R src-tauri/android-plugin/jniLibs/x86_64 \
     src-tauri/gen/android/app/src/main/jniLibs/
   npm run tauri android build -- --apk --target x86_64 --ci
   ```

   Building both targets from one shared `jniLibs` directory makes every APK fat, even
   when `--split-per-abi` is supplied. For Google Play, build an AAB and let Play deliver
   the device-specific split.

9. Verify every generated APK before uploading it:

   - reject any `.dll` entry;
   - reject files containing `version https://git-lfs.github.com/spec/v1`;
   - require `lib/<abi>/libmpv.so` and `lib/<abi>/libplayer.so`;
   - check the version name/code with Android tooling;
   - run `apksigner verify --verbose`.

10. Upload the verified split APKs as named release assets, for example `SingularityV2-arm64-v8a.apk` and `SingularityV2-x86_64.apk`. Do not upload an unverified local APK over the CI artifact.

## ABI policy

The default release targets are:

- `arm64-v8a` for current physical Android phones and tablets;
- `x86_64` for supported x86 Android emulators or devices.

Add `armeabi-v7a` or `x86` only if the project intentionally restores support for those older/rare devices and has the matching Rust and MPV libraries. A universal APK is allowed as a convenience asset, but it will be larger.

## Release checklist

Before creating a new Android release:

- Confirm the tag version matches `package.json`, `src-tauri/tauri.conf.json`, and the Android version metadata.
- Confirm the native-library bundle version and checksums are unchanged or intentionally updated.
- Run the workflow from the tag, not from a dirty working tree.
- Download the exact APK produced by the workflow and inspect its contents.
- Install the architecture-specific APK on a representative device and confirm startup, MPV initialization, and stream playback.
- Publish the checksums with the release notes.

Because `v0.6.3` already exists, a corrected packaging pipeline should normally be released under the next version (for example `v0.6.4`) rather than silently replacing the old artifact.

## Device selection example

The Galaxy Z Fold 7 uses a Snapdragon 8 Elite for Galaxy, which is an ARM64 mobile platform. Install the **`arm64-v8a` APK**. The `x86_64` APK is for x86 Android emulators/devices, not the Fold 7.
